# 2026年10月の改善と結果のまとめ

対象期間は2026年10月2日〜27日。研究テーマ「室内監視における小物体（鍵）追跡」の予備実験に向けて行った改善と、その結果をまとめる。

**注意**：以下の検出率は、特記がない限り**正解枠のない目安**（「検出が出たか」を数えたもの）である。正式な検出率は、正解枠の注釈後に `evaluate` で求める。評価に使った実映像は各条件1本で、カメラを手で動かしているものも含む。

### 2.3 記録が確定しない不具合の修正（10/6〜10/9）
- **現象**：Ctrl+Cで終了しても、記録が未完了（`complete: false`）になる。
- **原因**：起動スクリプトの `os.execv` が、Windowsではアプリを裏で動く別プロセスにし、Ctrl+Cがアプリに届かなかった。
- **修正**：子プロセスとして起動し、終了まで待つ方式に変更した。実際のコンソールでCtrl+Cを送る試験で、修正前は届かず、修正後は記録が確定することを確認した。

### 2.4 起動直後のフレーム欠落の修正（10/12）
- **現象**：起動から2.3秒の時点で4フレームが欠落した。
- **原因**：YOLOの読み込み中に受信が約1.4秒止まり、その後に約25枚がまとめて届いて、書き込み待ちの枠（16枚）があふれた。
- **修正**：書き込み待ちの枠を64枚に拡大した。同じ届き方の再現で、欠落13枚が0枚になった。

### 2.5 記録の開始・終了をボタンで操作（10/13）
- 起動しただけでは記録しない。PCの結果画面と、android-camera-streamerアプリの「Start/Stop recording」で操作する。
- 開始から終了までを1つの撮影セッション（記録ID）とし、`recordings/<記録ID>/` に保存する。Pythonを起動し直さずに何本でも撮れる。
- スマホのアプリは、`/video` に接続してきたPCのアドレスへ要求を送るので、アドレスの設定は不要。
- PC側の待ち受けは `127.0.0.1` とTailscaleのIPのみ。外部サイトからの操作を防ぐため、JSON形式の要求だけを受け付ける。
- 推論ログに `recording_id` と `raw_frame_id` を記録し、元画像と対応付けられるようにした。
- 確認：記録（40.4秒・689枚・欠落0）が正常に確定した。

### 4.2 大きく写った鍵を見つけられない問題（10/26〜10/27）
- **現象**：近距離の鍵（モデル入力上で約270px以上）をほぼ見つけられない（入力1280pxで1%）。学習データの鍵がほとんど小さいため。

- **対策**：学習画像の鍵の周りを切り抜いて拡大した画像（鍵が一辺の20〜80%を占める。拡大はbicubicとFSRCNNを半々）を、鍵の画像1枚あたり2枚加えた。
- **開発用の検証**（撮影日で分けたデータ）：大きく写した鍵の検証画像で 2% → 47%。

## 5. 切り出しと再検出の比較（10/27）

### 5.1 切り出し候補の拡張
余白を10/20/50/100/200/300%の6段階にし、倍率に「切り出しのみ（x1）」を加えた。同じ余白なら、超解像の倍率を変えてもモデルが見る鍵の大きさは同じになる（YOLOが640pxに拡大し直すため）。そのため、超解像の役割は「拡大の画質」だけになる。

### 5.2 候補ごとの再検出率（遠距離映像、30秒以降、鍵は主に24〜32px）

| 候補 | 再検出率 | 平均処理時間 |
|---|---|---|
| **余白100%・切り出しのみ** | **81%** | **11.7ms** |
| 余白200%・SR x4 | 80% | 56.7ms |
| 余白200%・切り出しのみ | 77% | 11.9ms |
| 余白200%・SR x2 | 74% | 22.7ms |
| 余白10〜20%・SR x4/x8（固定方式・規則方式の範囲） | 34〜38% | 17〜36ms |
| 余白300%・切り出しのみ | 39% | 11.7ms |

### 5.3 超解像が「近すぎて効かなかった」可能性の検証
鍵がはっきり写ったフレーム60枚を縮小してJPEG圧縮し、鍵を中央値14px（4〜27px）まで小さくして比べた。局所の再検出には、正しい鍵の位置を与えている。

| 縮小率（鍵の中央値） | 全画面検出 | 切り出しのみ | bicubic x2 | SR x2 | SR x8 |
|---|---|---|---|---|---|
| 1/4（20px） | 12/60 | 57/60 | **59/60** | 50/60 | 41/55 |
| 1/6（14px） | 8/60 | 50/60 | **54/60** | 50/60 | 38/59 |

→ 小さい鍵でも、FSRCNNは通常の拡大以下だった。全画面の検出は大きく落ちるが、**位置さえ分かっていれば、切り出して見直すだけで8〜9割を取り戻せる**。

### 5.4 比較実行の不具合修正（追跡のずれ）
- **現象**：fixed（余白20%・SR x4）が、通常の検出が見つけていた鍵を56フレーム取りこぼした。
- **原因**：拡大した切り出し画像で、鍵束の一部分（キーホルダーなど）が高い信頼度で検出され、それを採用したことで追跡する枠が縮み（70×53px→22×14px→10×12px）、以後の通常の検出と結び付かなくなった。
- **修正**（比較実行とライブ画面で共通）
  - 通常の検出があるときは、重なり（IoU）0.5以上の同じ物体だけを採用する
  - 予測位置しかないときは、面積の比が0.25〜4倍の範囲に限る
  - 追跡では、予測した枠の半分以上を包み込む検出を同じ物体とみなす
- **結果**（遠距離映像754フレーム、検出ありのフレーム数）

| 方式 | 修正前 | 修正後 | baselineが見つけたのに見失った | 処理時間（中央値） |
|---|---|---|---|---|
| baseline | 416 | 416 | — | 18.9ms |
| fixed（余白20%・SR x4） | 423 | 474 | 56 → **16** | 37.8ms |
| bicubic（余白20%・通常拡大x4） | 472 | 492 | 22 → 10 | 28.7ms |
| rule（x2/x4/x8規則） | 485 | **500** | 22 → 14 | 53.8ms |

### 5.5 超解像で精度が下がる原因の調査（10/27）
5.2・5.3節の「FSRCNNは通常の拡大以下」という結果の原因を、順に切り分けた（`scripts/probe_enlargement.py`）。

| 仮説 | 確かめ方 | 結果 |
|---|---|---|
| 実験の組み方の誤り | 「切り出しのみ」と「1回の双線形拡大で640pxへ」を比較 | 完全に一致（YOLO内部の拡大は双線形）。組み方は正しい |
| JPEG圧縮との相性 | 圧縮なし・品質75・品質50で比較 | 圧縮なしでもFSRCNNが低い → 否定 |
| x2モデルの重ねがけ | x4専用モデルと比較 | 専用モデルでも低い → 否定 |
| 輪郭の鋭さ | FSRCNNをぼかす／双線形に輪郭強調をかける | ぼかしても戻らず、輪郭強調では上がる → 否定 |
| 位置・色のずれ | 位相相関、YCrCbの差 | ずれは実質ゼロ。差は輪郭の細部だけ（平均1.4/255） |
| **検出器の不安定さ** | 小さな変化（雑音・再圧縮・1pxずらし）と、別の学習で作った検出器で比較 | **FSRCNNで、最終モデルは下がり（0.84→0.58）、開発用モデルは上がった（0.58→0.66）**。1pxずらすだけでも80個中11〜13個の信頼度が0.2以上変わる |

あわせて、最近傍で拡大すると検出率が0%になるなど、鍵の検出器は拡大の見た目のくせに非常に敏感だった。一方、COCOの汎用モデル（カップ）では、FSRCNNでも信頼度はほとんど変わらなかった。

→ **5.2・5.3節の超解像に関する結果は、1つの検出器だけに基づくもので一般化できない。** 超解像の効果は、検出器を複数回学習したときのばらつき、または汎用モデルでの再現を確かめて判断する。どちらの結果でも、超解像が精度を大きく上げることはなかった。

## 7. 今後：低スペックのデバイスを前提にした拡大方法の比較方針
研究目標に「比較的低スペックのデバイスへの組み込み」があるので、精度だけでなく、**処理時間とのバランス**で評価する。

### 7.1 評価のしかた
- **精度と処理時間の両方で比べる**：鍵の大きさ別の再検出率と、1回あたりの追加の処理時間を並べ、精度と処理時間のバランスで劣らない方法（パレート最適な方法）を選ぶ。補助の指標として「処理時間1msあたりの検出率の上積み」も見る。基準は「切り出しのみ」とする。
- **低スペック環境を想定した計測**：開発用PCのGPUの数字は参考にとどめる。CPUのみ・スレッド数を制限した条件（例：4スレッド）で計測し、あわせてモデルのパラメータ数と計算量も記録する。組み込み先の機種（例：Raspberry Pi 5、Jetson Orin Nano、スマートフォン）が決まれば、その機種で計測する。
- **1フレームあたりの平均の負荷**：再検出は「不安定なとき」だけ行うので、`発動率 × 1回の処理時間` を全画面の検出に足した平均時間で評価する。
- **処理時間の上限を先に決める**：例として、目標のフレームレートから1フレームあたりの上限（例：10fpsなら100ms）を決め、それを超える方法は精度が高くても採用しない。

### 7.2 比べる拡大方法（軽量なものに絞る）

| 方法 | 規模の目安 | 位置付け |
|---|---|---|
| 切り出しのみ（YOLO内部の拡大） | 追加の計算なし | 基準 |
| bicubic | ほぼ計算なし | 現時点の最有力 |
| FSRCNN（現行） | 約1万パラメータ | 現行の超解像 |
| ESPCN | 約2万パラメータ | 最軽量級の超解像。OpenCVで差し替え可能 |
| 効率重視の軽量超解像（SPAN、RLFNなど） | 数十万パラメータ | 画質と速度のバランス型。採用候補になりうるか確認 |
| EDSR、Real-ESRGAN、SwinIRなど | 1,000万パラメータ以上 | **低スペックでは使えない前提**。精度の上限の参考として、必要な場合だけ測る |

パラメータ数は文献上のおおよその値で、導入前に確認する。

### 7.3 公平に比べるための注意
- 今の最終モデルは、bicubicとFSRCNNで拡大した画像も混ぜて学習している。ほかの超解像は不利になるので、拡大方法ごとに学習用の拡大画像を作るか、超解像を含めずに学習した検出器を基準にして比べる。
- 人工的に縮小した映像に加え、ボケ・雑音・圧縮を加えた映像と、実際に遠くから撮った映像でも確かめる。
- 現時点では、切り出しのみ・bicubicが精度と処理時間の両方で有利である。超解像は、**処理時間の増加に見合う上積みがあるときだけ**候補に残す。
